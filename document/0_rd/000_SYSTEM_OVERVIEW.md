## システム概要

| 項目           | 内容                                                                                                                                             |
|----------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| システム名     | wakasaba_orchestrator                                                                                                                            |
| 目的           | 複数のLinuxサーバに対して定型メンテナンス処理（OS更新・PaperMCサーバ更新・バックアップ等）を自動実行するオーケストレーションバッチ               |
| 実行形式       | コマンドラインバッチ（Fat JAR）                                                                                                                  |
| 実行契機       | 手動実行（スケジューラ等からの呼び出しを含む）                                                                                                   |
| 実行コマンド例 | `java -jar wakasaba_orchestrator-1.0-SNAPSHOT-all.jar <server0_file> <server1_file> <server2_file> <server3_file> <server4_file> <server5_file>` |

---

## 背景・目的

- 複数台のLinuxサーバ（Minecraftサーバを含む）の定期メンテナンスを手動で行うと、作業漏れ・手順ミスのリスクがある。
- 本システムはメンテナンス手順をプログラムとして記述し、一括・自動実行することで作業の確実性と効率化を実現する。
- PaperMC（Minecraftサーバソフトウェア）および関連プラグイン（Pl3xMap）の最新版への自動更新も対象に含める。
- Schubertシステム稼働サーバのOSメンテナンスおよびSchubertの停止・起動も対象に含める。
- VPNサーバとNASサーバのOSメンテナンスも対象に含める。

## 対象サーバ構成

| インデックス | 定数              | 役割             | 保守対象                                                           |
|--------------|-------------------|------------------|--------------------------------------------------------------------|
| 0            | `SERVER_TEST`     | テスト           | OS更新・再起動・共有解除と復旧                                     |
| 1            | `SERVER_PAPER`    | PaperMC          | OS更新・再起動・共有解除と復旧・PaperMC停止/バックアップ/更新/起動 |
| 2            | `SERVER_LLM`      | ローカルLLM      | OS更新・再起動・共有解除と復旧                                     |
| 3            | `SERVER_SCHUBERT` | Schubert         | OS更新・再起動・共有解除と復旧・Schubert停止/起動                  |
| 4            | `SERVER_VPN`      | VPN              | OS更新・再起動・共有解除と復旧                                     |
| 5            | `SERVER_NAS`      | NAS              | OS更新・再起動。自身への共有操作は行わない                         |
| 管理端末     | -                 | 本バッチ実行端末 | 固定待機・時刻取得、最後にOS更新・60秒遅延再起動                   |

全6台の接続情報を先に読み込み、初期疎通不可の場合は全体の保守を開始しない。

## 実行環境・制約条件

NAS以外のリモート5台に `/nas`・`/share` のマウント設定、`findmnt`、必要なsudo権限が存在すること。
マウント先の共有元の正しさはサーバ設定で担保すること。

| 項目                 | 要件                                                                                                                          |
|----------------------|-------------------------------------------------------------------------------------------------------------------------------|
| 実行プラットフォーム | Javaが動作するLinux環境                                                                                                       |
| Javaバージョン       | Java 21以上（`SequencedCollection`（`List.getFirst()` 等）および `HttpClient` の `AutoCloseable` 対応を使用するため）         |
| ビルドツール         | Gradle（Shadow Pluginによる Fat JAR生成）                                                                                     |
| リモートサーバOS     | aptパッケージマネージャが使用可能なLinuxディストリビューション（Debian/Ubuntu系）                                             |
| SSH認証方式          | 公開鍵認証（秘密鍵ファイルを使用）                                                                                            |
| ネットワーク要件     | 実行サーバからリモートサーバへのSSH接続可能なこと。外部API（PaperMC API、Modrinth API）へのHTTPS接続可能なこと                |
| 実行ユーザ権限       | `sudo` コマンドが使用可能なユーザでSSH接続できること（パスワードなしsudo推奨）                                                |
| ファイルパス         | リモートサーバ上の作業ディレクトリ・本番ディレクトリは `/home/mini/` 以下で固定。変更時は定数クラスの修正のみで対応できること |

## 機能要件一覧

### FR-01：コマンドライン引数の受付・検証

- システムはコマンドライン引数として正確に6つのファイルパスを受け付けること。
- 引数の数が6つでない場合、USAGEメッセージを標準出力へ表示し、処理を行わずに終了すること。

### FR-02：接続情報ファイルの読み込み

- 各引数に指定されたファイルパスから、SSHサーバへの接続情報（ホスト・ポート・ユーザ名・秘密鍵パス）を読み込めること。
- 接続情報ファイルは1行1値のテキストファイル（UTF-8）であり、順番に host / port / user / key を格納していること。

### FR-03：リモートサーバ（サーバ0・サーバ2・サーバ5）のOSメンテナンス

- SSH経由で以下のコマンドを順次実行できること。
    1. `sudo apt update`（パッケージリスト更新）
    2. `sudo apt upgrade -y`（パッケージアップグレード）
    3. `sudo shutdown -r now`（即時再起動）

### FR-04：PaperMCサーバ（サーバ1）のメンテナンス

PaperMC停止後、Schubert停止と共通の60秒待機を経て全台の共有解除・OS更新・再起動・復帰待ち・共有再接続を実施すること。
バックアップ、正式版取得、SHA検証・配置は全台の共有復旧後に行い、最後にPaperMCを起動すること。

### FR-05：PaperMC/Pl3xMap最新版の自動取得

- PaperMC公式APIの系列と候補をAPI応答順に探索し、ハイフン（`-`）を含むpre・rc等を除外して、最新正式版のバージョン文字列を取得できること。
- 系列内に正式版がなければ次の系列を探索すること。全系列に正式版がなければ（空の一覧を含む）、`OTHER_PAPERMC_EXCEPTION`
  をメッセージとして `RuntimeException` を送出すること。
- 取得したバージョン文字列を用いてPaperMCビルド情報APIを呼び出し、最新ビルドのダウンロードURLを取得できること。
- 取得したダウンロードURLを用いてリモートサーバ上でwgetコマンドを実行し、JARファイルをダウンロードできること。
- Modrinth APIを呼び出し、Pl3xMapの最新バージョンのダウンロードURLを取得できること。
- PaperMCバージョンとPl3xMapの対応バージョンが一致しない場合、Pl3xMapのダウンロードをスキップすること。
- ダウンロードしたJARファイルは所定のダウンロード用ディレクトリへ保存すること。

### FR-06：JARファイルのSHAチェックサム検証・配置

- ダウンロードしたPaperMC JARのSHA-256チェックサムを検証し、一致した場合のみ本番ディレクトリへ移動すること。
- ダウンロードしたPl3xMap JARのSHA-512チェックサムを検証し、一致した場合のみ本番ディレクトリへ移動すること。
- Pl3xMapの旧バージョンのJARファイルは、バージョン一致・SHA検証の結果にかかわらず本番プラグインディレクトリから削除すること。
- SHA検証に失敗した場合、ファイル移動をスキップすること（エラーとして停止しない）。

### FR-07：VPNサーバ（サーバ4）のOSメンテナンス

- SSH経由で以下のコマンドを順次実行できること。
    1. `sudo apt update`（パッケージリスト更新）
    2. `sudo apt upgrade -y`（パッケージアップグレード）
    3. `sudo shutdown -r now`（即時再起動）

### FR-08：自サーバのOSメンテナンス

- ローカルBashコマンドとして以下の処理を順次実行できること。
    1. `sudo apt update`（パッケージリスト更新）
    2. `sudo apt upgrade -y`（パッケージアップグレード）
    3. 60秒遅延後の再起動（`(sleep 60 && sudo shutdown -r now) &`、バックグラウンド実行）

### FR-09：Schubertサーバ（サーバ3）のメンテナンス

PaperMCに続けてSchubert停止シェルを実行し、両コマンド完了後に管理端末で共通の60秒待機を行うこと。
全台の共有復旧とPaperMC更新・起動後にSchubert起動シェルを実行すること。

### FR-10：全機疎通確認・再起動後の復帰待ち

- 全6台の初期SSH疎通確認が保守開始条件であること。1台でも不可なら警告を記録し、管理端末も含め保守しないこと。
- 全台へ再起動指示後に管理端末で60秒待ち、各サーバを `SERVER_REBOOT_WAIT_LIMIT = 600` 秒目安で順に復帰待ちすること。
- SSH接続確認は `session.connect(60000)` を使用し、失敗試行後は1秒待って再試行すること。
- 期限超過は失敗した試行の後に検出して例外とすること。最後の試行が成功すれば期限後でも続行すること。
- 通常のコマンド実行前待機は1引数版を用い、上限を `Integer.MAX_VALUE` 秒とすること。

### FR-11：工程単位の実行とOS更新の並列化

```
1. setConnectionInformation(servers): 6ファイルを読み込み cis[0]～cis[5] を設定
2. isAllAlive(cis): 引数順に確認前ログを追記しSSH疎通確認
   最初の疎通不可 → WARNING: Servers Not Active → 保守せずMainへ復帰
3. systemStop(cis): PaperMC停止 → Schubert停止 → 管理端末で60秒待機（1回）
4. allUMount(cis): サーバ0～4の /nas・/share を解除し、findmntの出力がないことを確認
5. allUpdate(cis): サーバ0～5を並列更新（各台 update → upgrade）
   全スレッドのjoin → 引数順の例外検出 → 全件正常なら次工程へ
6. allReboot(cis): サーバ0～5へ順に再起動指示
7. BashExec.waitOneMin(): 管理端末で60秒待機（1回）
8. allRebootComplete(cis): サーバ0～5を順に確認（各呼び出し600秒目安）
9. allMount(cis): サーバ0～4の /nas・/share を接続し、findmntの出力があることを確認
10. systemPreSetup(cis): サーバ1でバックアップ → PaperMC/Pl3xMap取得 → SHA検証・配置
    wgetPaperMcの末尾で、管理端末のpapermc_version.txtを更新
11. systemStart(cis): PaperMC起動 → Schubert起動
12. 管理端末: 区切りログ → BashExec.update() → upgrade() → shutdown()
13. Mainで終了時刻記録・ログファイル出力
例外発生: 後続工程中止 → Mainでスタックトレース・終了ログ出力 → 手動復旧
```

工程ごとに対象全台を処理すること。OS更新はサーバごとにスレッドを開始し、各台ではupdate後にupgradeを実行すること。
全更新スレッドの終了と例外有無を確認してから再起動へ進むこと。その他の工程は従来どおり直列実行とすること。

### FR-12：実行ログの記録・ファイル出力

- 共有ログの宣言型は `List<String>`、実体は `Main` が生成する `CopyOnWriteArrayList<String>` とする。各クラスは同一インスタンスを参照する。
- 並列更新中の `add`・`addAll` は安全に実行できるが、コマンド行と標準出力を一体で排他しないため、サーバ間のログは混在する。サーバ別の順序・まとまりは保証しない。

- バッチ開始時刻・終了時刻をログに記録すること。
- 各リモートサーバの初期疎通確認前に接続情報を記録し、管理端末の保守開始時に区切りログを記録すること。
- 実行したコマンドおよびその標準出力をログに記録すること。
- ワークフロー実行中の例外はスタックトレースとしてログに記録すること。
- ワークフローの正常・異常終了にかかわらず、収集したログをファイルへ出力すること。
- ログファイル名は終了時刻のタイムスタンプ（yyyyMMddHHmmss形式）を含むこと。

### FR-13：PaperMCバージョンファイルの出力

- PaperMC・Pl3xMapのダウンロード処理後、管理端末上の `papermc_version.txt` に取得対象のPaperMCバージョンを出力すること。
- Pl3xMapのダウンロードをバージョン不一致でスキップした場合も出力すること。SHA検証・本番配置前に出力し、本番配置・起動完了を示す情報とはしないこと。
- バージョン文字列のみを末尾改行なしで新規作成または上書きすること。初期疎通不可による全体中止や出力到達前の例外発生時は更新しないこと。

### FR-14：NAS共有の解除・復旧

- NASをサーバ5としてOS更新・再起動・復帰確認の対象に含めること。
- NAS以外のリモート5台で `sudo umount /nas` → `sudo umount /share` を実行し、各 `findmnt` の出力がないことを確認すること。
- 全台復帰後は `sudo mount /nas` → `sudo mount /share` を実行し、各 `findmnt` の出力があることを確認すること。
- マウント有無が期待と異なる場合は実行時例外で後続工程を中止すること。管理端末は共有操作対象に含めないこと。

## 非機能要件

### NFR-01：信頼性

- 各コマンドの実行・出力はすべてログへ記録し、実行後に内容を確認できること。
- JARファイルの配置前にチェックサム検証を行い、不正なファイルの配置を防止すること。

### NFR-02：保守性

- 実行環境（ファイルパス・コマンド文字列・URL・ログフォーマット等）に依存する値はすべて定数クラス（`WksConstants`
  ）に一元管理し、修正を1箇所に集約できること。
- パッケージ・クラスの責務を明確に分離し、各クラスが単一の責務を持つこと。

### NFR-03：セキュリティ

- SSHの秘密鍵ファイルパスはログへ出力しないこと。
- SSH接続情報ファイルのパーミッションは600（所有者のみ読み書き可）に設定することを推奨すること。

### NFR-04：移植性・拡張性

- Fat JARとして単一ファイルで配布・実行できること。
- 接続情報ファイルを変更することで、対象サーバのIPアドレス・ポート・ユーザ・秘密鍵を変更できること。

## 例外・エラー要件

### ER-01：基本方針

- 更新スレッド内の例外は保存し、全スレッドの終了待ち後に親スレッドで引数順に検出する。
- `JSchException`・`IOException`・`InterruptedException` は同じ例外を再送出し、その他の `Exception` は原因を保持した
  `RuntimeException` で再送出する。
- 親スレッドで例外を再送出した場合は、再起動以降を実行せず、従来どおりMainでログ出力して手動復旧する。
- 更新失敗時もほかの開始済みタスクはキャンセルせず、終了を待つ。複数の失敗は集約せず、引数順で最初に検出した例外を再送出する。

- マウント状態不一致・SSH復帰待ち超過は実行時例外とし、後続工程を実行しないこと。
- 例外時はSchubert起動を含む残りの工程を打ち切り、自動復旧せず手動復旧すること。


- 業務メソッドで発生した検査例外は `throws` 宣言で上位クラスへ委譲し、非検査例外も含めて最終的に `Main.main` まで伝播させること。
- `Main.main` はワークフロー実行中の `Exception` を捕捉し、スタックトレースをログへ追記した後、終了時刻記録とログファイル出力を行うこと。
- `Main.outLog` が送出する `IOException` はJVMへ伝播させること。

### ER-02：例外の種類と想定発生状況

| 例外クラス                               | 主な想定発生状況                                                                                                                            |
|------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| `IOException`                            | 接続情報ファイル読込失敗・SSH標準出力読取失敗・HTTPネットワーク障害・ログファイル書込失敗・ログ出力先ディレクトリ不在またはファイル生成失敗 |
| `InterruptedException`                   | SSH/HTTP待機中の割り込み・ローカルプロセス待機中の割り込み                                                                                  |
| `JSchException`                          | SSHセッション生成失敗・SSH接続失敗・チャンネル接続失敗                                                                                      |
| `FileNotFoundException`（`IOException`） | 管理端末上のPaperMCバージョンファイルのオープン失敗                                                                                         |
| `RuntimeException`（非検査）             | PaperMCの全系列に正式版が見つからない場合                                                                                                   |
| `NumberFormatException`（非検査）        | 接続情報ファイルのポート番号が整数値でない                                                                                                  |
| `IndexOutOfBoundsException`（非検査）    | 接続情報ファイルが4行未満                                                                                                                   |

### ER-03：SSH疎通確認の特例

- `isAlive()` 内の `session.connect(60000)` が投げるすべての `JSchException` は `false` として吸収すること。
- `SshCommand.waitForBecomeActive()` から呼び出される場合は、`false` の間、指定上限を超えるまでポーリングを継続すること。
- 初期疎通判定がfalseの場合は全体の保守を開始せず、警告を記録してMainへ復帰すること。
- `getSessionInstance()` 内での `JSchException`（秘密鍵読込失敗等）は吸収せず上位へ伝播させること。
